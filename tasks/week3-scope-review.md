## 已砍掉 / 延后的功能

### 1. Escrow 合约（付款但不交付的处理）

**为什么砍掉：**
实现 Escrow 需要额外的智能合约部署和仲裁机制，工程量大且超出了「Agent 自主支付」这个核心 demo 的边界。MVP 阶段接受「信任 Worker 会交付」的前提。

**记录为已知局限：**
```
已知局限：付款后 Worker 可以拒绝交付数据。当前方案依赖 Worker 的信誉，
没有 Escrow 机制。真实产品需要链上 Escrow + 仲裁层。
```

---

### 2. 数据质量自动验证

**为什么砍掉：**
验证「数据是否准确」需要对比多个来源或人工判断，超出当前 Agent 能力边界。MVP 保留人工验收作为最终确认。

**替代方案（已记录）：**
报告页脚显示数据来源 URL，用户可自行核对。

---

### 3. Agent 身份链上声明（ERC-8004）

**为什么砍掉：**
ERC-8004 Agent 身份声明在 MVP 阶段不是核心功能——两个 Agent 之间已经通过 tx hash 证明了支付关系。链上身份声明是后续 reputation 体系的前置，不影响当前 demo。

**延后到：** 长期路线图

---

### 4. Reputation Layer（Worker 信誉评分）

**为什么砍掉：**
防止 Sybil attack（假 Worker 低价吸引付款但返回垃圾数据）需要历史评分记录。这需要链上存储或中心化评分服务，超出 Hackathon 时间范围。

**记录为已知漏洞：**
```
已知漏洞：Sybil attack — 攻击者注册大量 Worker，刷低价吸引 Agent 付款
但返回垃圾数据。根本修法：reputation layer。MVP 阶段接受此风险。
```

---

### 5. 多轮对话 / 对话历史管理

**为什么延后：**
当前 Agent 是单轮：用户输入 → Agent 执行 → 报告输出。多轮对话（「刚才的 ETH 价格是多少？」）需要 session 管理，超出 MVP 范围。

**当前行为：** 每次运行独立，不保留历史

---

### 6. 前端 UI

**为什么延后：**
CLI 工具已足够演示核心功能，前端 UI 会分散开发精力。Hackathon 评审关注技术深度，不是 UI 美观度。

**Demo 格式：** 终端录屏 + 语音解说

---

### 7. 主网部署

**为什么砍掉（永久）：**
Hackathon 阶段不在主网操作。全程使用 Sepolia 测试网。

---

## 当前 MVP 边界

**包含：**
- 自然语言接收任务
- HTTP 探测发现 Worker（本地 3 个 Worker）
- LLM 推理比价选择
- 429 触发 CAW 支付（Sepolia）
- x402 验证 + 真实 API 数据
- Markdown 报告 + tx hash 页脚

**不包含（上方已说明原因）：**
- Escrow 合约
- 数据质量自动验证
- ERC-8004 身份
- Reputation 评分
- 多轮对话
- 前端 UI
- 主网

---

## 防范 Week 4 范围膨胀的规则

1. **新功能申请制**：每个新想法写一句话说明「为什么这个比 Demo 视频更重要」，不能说服自己就不做
2. **Demo 视频优先**：任何阻碍 Demo 视频完成的功能都推后
3. **文档也算产出**：把已知漏洞和边界写清楚，比新加一个功能更有价值
