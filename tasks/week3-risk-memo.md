## 项目成立依赖的关键前提

**假设：** CAW Pact 的白名单和金额限制在合约层强制执行，不能被 Agent 代码绕过。

**假设：** 存在或将要存在愿意用 x402/429 机制提供付费 API 的服务提供方。

## 最可能失败的地方

### 风险 1：合法浪费攻击（Legitimate Waste Attack）

**描述：** 攻击者操控用户输入，让 Agent 反复查询无用数据。每次支付都在 Pact 范围内，但累积耗尽 Agent 预算。

**严重程度：** 中（预算有上限，损失可控）

**当前防线：** rate limit（每分钟 2 次免费调用限制）+ Pact 的总交易次数限制

**根本修法：** session token 绑定请求方身份，让 Agent 能识别「同一个用户的合理查询」和「恶意刷量」的区别。超出 MVP 范围，已记录为已知漏洞。

---

### 风险 2：Sybil Attack（假 Worker）

**描述：** 攻击者注册大量 Worker，刷低价格（如 0.0001 SETH）吸引 Agent 选择，但返回垃圾数据或不返回。

**严重程度：** 中（Pact 限制了单次损失，但体验很差）

**当前防线：** 无（MVP 接受此风险）

**根本修法：** Worker reputation layer，需要历史记录 + 质押机制。超出 Hackathon 范围。

---

### 风险 3：LLM 推理错误选 Worker

**描述：** LLM 看到 Worker 列表后，选了不适合当前查询的 Worker（如用「价格 Worker」回答「TVL」问题）。

**严重程度：** 低（付了钱但数据不对）

**当前防线：** 每个 Worker 的 `/catalog` 接口清晰描述能力，降低 LLM 误判概率

**Fallback：** 报告生成时 LLM 会指出数据来源不匹配，用户可以重新查询

---

### 风险 4：Demo 录制时网络/环境问题

**描述：** 录 Demo 视频时 Sepolia 网络延迟或 LLM API 限速，导致演示效果差。

**严重程度：** 低（对 Hackathon 提交影响最大）

**Fallback 计划：**
- 提前录多次，用最好的那次
- 如果链上部分不稳定，用已有 tx hash 演示
- 视频配文字说明，补充运行时截图

## 已通过验证的论点

（可以放心在 Week 4 提交和评委问答中使用）

1. ✅ **CAW vs EOA**：信任边界位置不同，CAW 约束在合约层，防 prompt injection 更有效
2. ✅ **Go server 的经济身份**：持有独立钱包、自主验证、没有中间人，是经济参与者不是 API
3. ✅ **合法浪费攻击**：已知漏洞，有第一道防线，真正修法是 session token 绑定
4. ✅ **x402 生态假设**：CAW Pact 信任边界模型独立于 x402，即使支付层不普及，Agent 预算控制问题今天就存在
