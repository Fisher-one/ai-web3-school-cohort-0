## 学习笔记

### Agent Wallet（智能体钱包）— 5/29 读完，explain-back 完成

**核心问题：为什么不能直接把钱包私钥给 Agent？**

Agent 的判断来自模型 + 上下文 + 工具返回值，是个概率系统。会幻觉、会被 Prompt Injection 带偏、会被恶意文档诱导。链上交易不可逆，把私钥交给一个概率系统等于裸奔。

**两个极端，中间那条路：**
- 左端：Agent 只能建议不能执行 → 停在「生成方案」，永远出不了产品
- 右端：权限全给 → Demo 很顺，真实用户不敢用
- 中间那条路：**Agent 可以执行，但只能在用户预先允许的边界里执行**

**第一性原理：控制权不能交给概率系统。Agent 只能拿到可验证、可限制、可撤销的行动空间。**

三条设计原则：
1. Agent 不直接控制主资产 — 模型可以生成交易草稿，不拿主私钥，高风险交还给人
2. 钱包不只是签名按钮，而是权限系统 — 要表达时间、金额、合约、方法、资产、接收方、撤销条件
3. 自动化必须绑定撤销能力 — 用户随时能看见 Agent 拿了什么权限、做过什么、还能做什么、在哪关掉

**9 个知识节点，按我理解的顺序串起来：**

| # | 节点 | 我的理解 |
|---|------|----------|
| 1 | AA Wallet | 基于 ERC-4337 的智能钱包，不是换 UI，是让账户本身能表达规则。传统 EOA = 一把私钥控制一个账户，AA = 账户里可以写逻辑。 |
| 2 | Smart Account | AA 的具体实现 — 带规则的钱包合约。能定义：谁可以操作、单日限额、白名单合约、权限失效时间、异常暂停。Agent 的执行边界就在这。 |
| 3 | Safe | 多签 + 模块化智能账户。核心价值是把执行权拆开——Agent 生成草稿或触发低风险模块，但大额转账/合约升级必须多签人确认。Agent 参与流程但不独占最终控制权。 |
| 4 | Session Key | 临时、有限权限的「小钥匙」。让 Agent 在规定时间内、规定范围内自动签名。不是小号私钥，是一组受限能力。必须限制：时间、合约白名单、单笔/总金额、资产类型、是否允许转出、可随时撤销。 |
| 5 | Policy | Agent 每笔链上动作必须遵守的规则，写成系统可检查的条件。比如：日限额 10 USDC、只能 swap 不能无限 approve、滑点超 1% 就停、NFT 不能自动转出。Policy 要能回答「这笔操作到底有没有越界」。 |
| 6 | Guard | 确定性拦截层，不是 AI 判断，是硬规则。交易出去前再查一次：目标地址在白名单吗、金额超限吗、方法允许吗。Agent 负责生成候选动作，Guard 负责拒绝越界动作。 |
| 7 | Simulation | 交易发出前的预演。不只检查能不能发，还要翻译成人话：你会支付多少、收到什么、授权会变什么、失败损失什么。对用户来说，这是理解交易的最后窗口。 |
| 8 | Revocation | 怎么收回权限。不只用户主动关，系统也该在这些情况下自动收紧：session key 到期、额度用完、多次失败、检测异常地址、Agent 偏离原始任务、用户长时间没确认。原则：所有自动化权限都要有一个用户看得见的关闭入口。 |
| 9 | Human Check | 分层确认，不是所有事都丢回给人：低风险小额自动执行 → 中等风险先模拟再确认 → 高风险不可逆必须展示影响并确认 → 超出 policy 直接拒绝不问用户。 |

**Session Key vs Policy 的区别（我之前没搞清楚，Agent 帮我纠正了）：**

- Session Key = 能力层。给你一把受限钥匙，限制你能操作的合约、方法、金额、时间。Agent 拿着钥匙去签名。
- Policy = 执行层。即使有钥匙，每笔交易还要再过规则引擎。不只限制人，还限制时机、状态、上下文——滑点超没超、市场状态变了没、授权额度是否异常。

类比：Session Key = 门禁卡（只能进 3 楼，今晚 12 点失效），Policy = 每个房间门口的规则引擎（今天限流、没预约不能进）。

**Guard vs Simulation：为什么两个都要？**

Simulation = 「这笔交易你会失去什么、得到什么」（帮你理解，概率性）
Guard = 「这笔交易能不能发」（帮你拦死，确定性）

顺序：Simulation 先跑（让人看懂），Guard 再检查（确定性拦截），两个都过了才签名。

**正确的交易流水线（我之前搞错了顺序）：**

```
Session Key 授权（一次性，限定范围）
  → Agent 生成交易
    → Policy 规则检查 ← 超限直接拒，别浪费资源模拟
      → Guard 确定性拦截 ← 不在白名单直接拒
        → Simulation 模拟结果 ← 翻译成人话
          → Human Check 分层确认
            → 低风险自动执行 / 中风险模拟后确认 / 高风险必须确认
```

我没搞懂的地方：最开始把 Policy 放在了 Simulation 和 Human Check 之后，这不对——如果交易本身就超了 policy，Guard 应该直接拦死，不该浪费资源去模拟，更不该拿去问用户「要不要继续」。Handbook 原话：「超出 policy 的动作：直接拒绝，而不是问用户要不要继续」。

**还没搞懂的：**
- Safe 的 Guard 和 Agent Wallet 的 Guard 是不是同一个东西？如果 Agent 通过 Safe 执行，Guard 是 Safe 层面的还是独立的一层？
- Simulation 在跨链场景下怎么处理？各链状态不一样，模拟准确性怎么保证？
